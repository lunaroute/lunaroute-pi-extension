# CI for lunaroute-pi-extension

Date: 2026-08-12

## Goal

Add continuous integration to `lunaroute-pi-extension`: sanity gates on every
push and pull request, and tag-driven npm publishing using npm's modern
Trusted Publishing + provenance flow. Plus one new unit test that closes the
biggest coverage gap in the v2 auth path.

## Context

The repo currently has no `.github/` directory and no CI. It is hosted on
GitHub (`git@github.com:lunaroute/lunaroute-pi-extension.git`), so GitHub
Actions is the natural CI provider. The package is a scoped npm package
(`@lunaroute/pi-extension`, `publishConfig.access: "restricted"`) and is not
yet published.

The existing in-repo check is `npm run check` = `tsc --noEmit` + `vitest run`
(42 tests on v2). CI runs that plus a package-file-list assertion.

### Dependency on v2

The pack-file-list assertion is tied to the v2 source layout (`src/index.ts`,
`src/lunaroute.ts`, `src/login.ts`, `src/discovery.ts` — 4 source files, 7
packed files total with `package.json`/`README.md`/`LICENSE`). v1 had a
2-source-file layout. **The CI sanity check therefore lands after the v2
branch merges** (or is rebased on top of v2). Building CI against main's v1
layout would ship an assertion that fails the moment v2 lands.

## Architecture

Two GitHub Actions workflows, plus one `package.json` addition and one new
test.

### Workflow 1: `.github/workflows/check.yml` — sanity gates

**Triggers:** `push` (any branch), `pull_request` (any target).

**One job, one Node version** (Node 22 LTS, matching the runtime Pi ≥0.84.1
requires; also satisfies npm Trusted Publishing's Node ≥22.14 floor for when
the same setup is reused by the publish workflow).

**Steps:**
1. `actions/checkout@v4`
2. `actions/setup-node@v4` with `node-version: "22"` and `cache: npm`
3. `npm ci`
4. `npm run check` (typecheck + 42 tests) — must pass
5. Pack-file-list assertion (inline `bash`, no third-party action):
   - Run `npm pack --dry-run`, capture the file list.
   - Assert the 7 expected files are present: `package.json`, `README.md`,
     `LICENSE`, `src/index.ts`, `src/lunaroute.ts`, `src/login.ts`,
     `src/discovery.ts`.
   - Assert no `tests/` file appears.
   - Fail the step if any expected file is missing or any test file leaks.

**Permissions:** `contents: read` (minimum for checkout + reading the repo).

**Concurrency:** cancel in-progress runs for the same branch when a new push
arrives (`concurrency: { group: ${{ github.ref }}, cancel-in-progress: true }`).

### Workflow 2: `.github/workflows/publish.yml` — tag-driven publish

**Trigger:** tags matching `v*` (catches both `v0.2.0` and `v0.2.0-beta.1`).

**One job, one Node version** (Node 22, matching the check workflow; satisfies
npm Trusted Publishing's Node ≥22.14 + npm CLI ≥11.5.1 floor).

**Steps:**
1. `actions/checkout@v4` (the tag)
2. `actions/setup-node@v4` with `node-version: "22"` and `cache: npm`
3. `npm ci`
4. `npm run check` (gates the publish — a tag that fails tests does not ship)
5. `npm publish --provenance --access restricted`

**Provenance / Trusted Publishing:**
- `permissions: { contents: read, id-token: write }`. `id-token: write`
  enables npm's OIDC trusted-publishing flow — **no `NPM_TOKEN` secret**.
  npm CLI auto-detects OIDC auth and prefers it before token auth.
- Requires a per-package Trusted Publisher entry on npmjs.com (see
  Prerequisites).

**Prerelease handling:** automatic. `npm publish` reads the version string
from `package.json` (which matches the tag since the tag is `v<version>`);
`0.2.0-beta.1` → `beta` dist-tag, `0.2.0` → `latest`. No workflow logic.

### `package.json` addition

Add the `repository` field — **required** for `npm publish --provenance`
(provenance attests against a public repo URL):

```json
"repository": {
  "type": "git",
  "url": "https://github.com/lunaroute/lunaroute-pi-extension.git"
}
```

No other `package.json` changes.

### New test: real `startLoopbackServer` coverage

Add to `tests/login.test.ts` a direct test of the real `startLoopbackServer`
(today every browser-login test injects a fake; the real `node:http` server
is untested). The test:

1. Calls `startLoopbackServer()` (real).
2. Makes an HTTP request to `http://127.0.0.1:${port}/callback?code=abc&state=xyz`,
   asserts the response is HTTP 200 with the success HTML body, and that
   `waitForCallback()` resolves with `{ code: "abc", state: "xyz" }`.
3. Makes a request to `/favicon.ico`, asserts HTTP 404.

This covers the 404 path, the `address()→port` extraction, and the HTML
response — the three behaviors today's tests only mock around. No new
dependencies; uses Node's built-in `fetch` against the real loopback port.
Closes deferred-minor M-5 from the v2 final review.

## Prerequisites (out of band, before publish works)

The publish workflow will fail with a clear npm error until the Trusted
Publisher is configured on npmjs.com. This is a one-time manual setup:

1. Sign in to npmjs.com as an owner of `@lunaroute/pi-extension` (the package
   must exist on npm first; the very first publish is a chicken-and-egg
   exception — see "First publish" below).
2. Add a Trusted Publisher entry:
   - GitHub organization/user: `lunaroute`
   - repository: `lunaroute-pi-extension`
   - workflow filename: `publish.yml` (filename only, no path)
   - allowed actions: `npm publish`
3. Ensure the package is public-readable or consumers have npm credentials
   with read access (the package is `publishConfig.access: restricted`, i.e.
   scoped-private).

### First publish (chicken-and-egg)

Trusted Publishing requires the package to already exist on npm. The very
first publish (`v0.2.0`) must be done **locally** with `npm publish
--access restricted --provenance` from a machine with `npm` authenticated,
then the Trusted Publisher entry is added, and all subsequent publishes go
through the workflow. Document this in the README.

## Error handling

- **Sanity check fails:** the PR/push is marked failing; nothing else happens.
  No publish.
- **Publish workflow's `npm run check` fails:** publish step is skipped (job
  stops). The tag is not published. The maintainer drops the tag, fixes, and
  re-tags.
- **`npm publish` fails (e.g. version already exists, Trusted Publisher not
  configured, provenance rejected):** the job fails with npm's error output.
  The tag is consumed only on successful publish.

## Testing strategy

- **Workflow files:** validated by running them. The sanity workflow is
  exercised on the PR that adds it (self-test). The publish workflow cannot
  be safely exercised until the first real tag; the first `v0.2.0-beta.1` tag
  serves as the dry run (prerelease dist-tag, not `latest`).
- **Pack-file-list assertion:** the inline `bash` step is the test. It fails
  loudly if `files` in `package.json` drops a source file or leaks a test
  file — the exact class of bug that left `pi.extensions` dangling in the
  v2 Tasks 1–5.
- **New `startLoopbackServer` test:** unit test in the existing vitest suite;
  runs as part of `npm run check`.

## Out of scope

- Lint job (the repo has no ESLint config; not worth adopting one for a
  4-file package).
- Node version matrix (single Node version).
- Dependabot / dependency auto-updates (separate concern).
- `npm audit` gate (the 3 high-severity findings are transitive deps the
  extension does not control; gating would be noise).
- Release notes / changelog automation.
- Publishing to any registry other than npm.
